# High-Energy Transient Reading Radar — V0.1 Execution Spec

> Status: Accepted — V0.1 decision frontier closed 2026-09-03  
> Purpose: define the executable contract for the five-Work model vertical slice

## 1. Objective

V0.1 validates the domain model and end-to-end architecture with five real Works selected for structural-risk coverage. It does not attempt launch-scale content coverage.

The acceptance invariant is:

$$
\boxed{\textbf{Stored}+\textbf{Validated}+\textbf{Rendered}}
$$

Every major domain structure must have a canonical stored representation, pass structural, referential, and semantic validation, and appear in one of the defined inspection layers.

V0.1 completion is objectively defined as:

$$
\boxed{\text{coverage matrix complete}+\texttt{local npm run verify = 0}+\text{remote CI = PASS}}
$$

The governance invariant is:

$$
\boxed{\text{V0.1 must prove not only that knowledge can be automated, but that automation cannot bypass Evidence and Human review boundaries.}}
$$

The delivery chain is:

$$
\boxed{\text{versioned specification}\rightarrow\text{traceable requirements}\rightarrow\text{verified implementation}\rightarrow\text{independently reproduced CI}}
$$

## 2. Technology Scope

V0.1 uses:

- Astro;
- TypeScript;
- YAML for canonical structured domain records;
- Markdown for canonical editorial reading prose.

Deferred:

- Pagefind until V0.2;
- MDX until a demonstrated content requirement exists;
- database or CMS;
- editing interface;
- standalone Research Map page.

V0.1 also excludes user accounts, authentication, bookmarks, reading-progress tracking, comments, reactions, email delivery, a CMS or administration UI, application-level Actor administration, automatic arXiv or ADS ingestion, LLM-generated summaries, automatic recommendations, semantic search, a graph database, and a complex interactive graph. Repository-governed Curation Actors and capability validation do not constitute an end-user permission system.

## 3. Canonical Content Boundary

- `content/` is the sole root scanned for canonical production content.
- `content/` is closed-world: every file, directory name, and extension must match the declared layout, and unknown entries are structural errors rather than ignored inputs.
- Work-owned structured records and reading prose live in Work-local bundles.
- Scientific Edges are global independent records, one Edge per file.
- YAML and Markdown join through immutable Work IDs.
- Small local records are canonical.
- Aggregate indexes are reproducible generated artifacts and are ignored by Git by default.
- Generated reverse indexes and other aggregate artifacts live under ignored root-level `generated/`; canonical loaders never scan that directory, and every artifact must be reproducible solely from `content/`.

The canonical content manifest stores only one global `schema_version`, a `canonicalization_version`, and an immutable named `visibility_profile_id`; it does not enumerate canonical files. The single Visibility Profile contains separate Work, Research Line, and Learning Path clauses, and every Reader Entity approval references that same release profile ID. Concern files do not carry independent schema versions. Unsupported versions fail explicitly, and migrations are explicit tested transformations rather than silent loader coercions. Validation reports record schema version, canonicalization version, validator version, visibility profile ID, and a deterministic canonical-content digest. V0.1 implements the named Visibility Profile directly in the validator and does not introduce a generic rules engine.

The Canonical Content Digest and every Visibility Digest use the same `canonicalization_version` and semantic SHA-256 procedure; only their input projections differ. For canonical content, relative paths are bytewise sorted, YAML is parsed and serialized with stable key ordering while preserving array order, and Markdown is normalized to UTF-8 with LF line endings while preserving content. Generated files, temporary caches, and test fixtures are excluded. Canonicalization rules are versioned so a rules change cannot silently alter digest meaning.

The canonical root begins with:

```text
content/
  manifest.yaml
  actors.yaml
  works/<work-id>/
    work.yaml
    versions.yaml
    evidence.yaml
    annotations.yaml
    statements.yaml
    physical-account.yaml
    reading.md
  scientific-edges/<edge-id>.yaml
  ontology/axes/<axis-id>.yaml
  methods/taxonomy.yaml
  research-lines/<line-id>/
    line.yaml
    reading.md
  learning-paths/<path-id>/
    path.yaml
    reading.md
```

Every canonical Work contains the complete fixed seven-file bundle. Empty concerns are represented by valid empty collections; a missing concern file is a structural error. Records are not split into one file per Version, Annotation, Statement, or Causal Link.

Physics Ontology uses one file per axis, with the axis definition, default Interpretive Risk, constraints, and Controlled Terms colocated under that axis. Exactly 16 Physics Axis IDs and the scientific question each asks are schema-level vocabulary; adding, removing, merging, or semantically changing an Axis requires a new schema version and explicit migration. Axis labels may change without changing identity, while terms beneath an Axis use ordinary Controlled Term lifecycle. Every visible Work has a completed assessment of all 16 Physics Ontology axes, so `not_assessed` is forbidden in its reader-visible projection. V0.1 Method Taxonomy remains one `taxonomy.yaml` containing Method Families, Canonical Techniques, and their relationships. Both families and techniques use the full Controlled Term lifecycle, immutable IDs, aliases, successor rules, and activation review; a semantic change to technique-family membership is a Material Change. Every visible Work has at least one reviewed Method Annotation that references an active Canonical Technique.

Method Annotations use a dedicated `basis: explicit | inferred` and do not carry Physics Annotation Interpretive Risk. Every Method Annotation references at least one Work-local Evidence record bound to a concrete Version. An Explicit Method Annotation may be self-reviewed by an eligible Human creator against its cited Evidence. An Inferred Method Annotation additionally requires a normalized reason and review by an eligible Human distinct from its creator. A Material Change to technique, basis, normalized reason, or Evidence references resets Review State to `unreviewed`; formatting-only changes do not.

Editorial contexts own their relations. Each Research Line bundle owns its independently reviewed memberships, contextual Reading Roles, and Editorial Anchor designations; each Learning Path bundle owns and atomically reviews its ordered membership and Pedagogical Transitions as one structured path. Human creators with `review_records` may self-review editorial records, while every Agent-created editorial record requires review by an eligible Human. Each Work–Research Line pair has at most one membership. Reading Roles form a non-empty deduplicated set using the frozen vocabulary `foundation | review | method | group_lineage | frontier | opportunity`; roles are context-local and `method` is not a Method Taxonomy assignment. A Material Change to a membership's Work endpoint, Reading Roles, or Editorial Anchor designation resets that membership to `unreviewed` and invalidates any affected Reader Entity approval. Every visible Work has at least one Research Line Membership and exactly one membership designated as its global Editorial Anchor; that anchor belongs to a visible Research Line. A visible Research Line contains at least one reviewed membership to a visible Work. Draft secondary memberships remain canonical but stay outside the reader-facing projection. Work bundles do not duplicate these relations. Generated reverse indexes allow Paper pages to render editorial membership and are non-canonical reproducible artifacts.

A Learning Path contains a duplicate-free ordered Work sequence. A path with N entries has exactly N-1 Pedagogical Transitions, each connecting one adjacent pair and carrying a normalized reason. A Material Change to path entries, entry order, transition endpoints, or transition reasons resets the entire structured path to `unreviewed` and invalidates its Visibility Approval. A visible Learning Path contains at least two entries and every referenced Work is visible.

Editorial bundle ownership is repeated once per file: the directory identifier, `line.yaml` or `path.yaml` identifier, and corresponding `reading.md` frontmatter identifier must match. Nested memberships, entries, and transitions inherit bundle ownership and do not repeat it.

Evidence records are canonical reusable Work-local provenance entities. Each references a concrete Version from the same Work and uses typed locator components. Annotations, Statements, Causal Links, and Scientific Edges reference Evidence IDs rather than duplicating locator data. Excerpts aid verification but do not replace provenance, and checksums exist only for actually preserved source snapshots.

### Identifier Invariant

IDs are immutable, namespaced, and human-readable, but their mnemonic components carry no parseable domain meaning. Metadata corrections never rename an allocated ID. Implementations and validators may check namespace syntax and uniqueness, but must never derive authorship, year, title, scientific classification, or any other domain fact from an ID string.

### Knowledge-completeness Invariant

Every Physics Ontology axis uses an explicit assessment state:

```text
present
unknown
not_applicable
not_assessed
```

`present` requires values, while all other states forbid values. `unknown` means assessed but scientifically indeterminate, `not_applicable` means the axis question does not apply, and `not_assessed` alone represents actionable curation debt. Optional bibliographic metadata may use explicit `null` and must never be guessed.

`not_assessed` remains generally legal curation debt, but the V0.1 fixture coverage profile forbids it for every Physics Ontology axis on all five fixture Works, and the V0.1 Visibility Profile forbids it across all 16 axes for every visible Work. `unknown` and `not_applicable` satisfy completed assessment. A violation is a coverage failure rather than a global warnings-as-errors policy.

### Work and Version Ownership

- Version owns title, authors, publication date, arXiv identifiers, DOI, journal, and other bibliographic metadata.
- Work owns immutable Work ID, a Preferred Version selection, and Work-level scientific structures.
- `Version.kind` is the closed V0.1 vocabulary `arxiv_revision | journal_manifestation`.
- Each curated public arXiv revision is a distinct Version identity. Revisions are recorded lazily when canonical records need them rather than exhaustively imported, and Evidence always binds to the exact curated revision.
- Every V0.1 Work with at least one Version explicitly selects a Preferred Version using `version_id`, reason, and Curation Provenance.
- The selection is an editorial choice and is not inferred from recency or reading convenience.
- Reader citation and display metadata derive from the Preferred Version.
- Changing the Preferred Version never changes Work identity.
- Evidence identity remains independently Version-specific and never migrates automatically with the Preferred Version.
- Work-level `reading.md` describes the Work rather than one Version.

Version authors are Version-local ordered records using source-specific `display_name` values with optional ORCID identifiers that are never guessed. Names are not forcibly split into given and family components, and V0.1 does not introduce a global Person identity. Every canonical Version requires `release_date: { value, precision }`, where `precision` is `year | month | day` and `value` is a strict matching Gregorian partial ISO value in `YYYY`, `YYYY-MM`, or `YYYY-MM-DD` form. Neither the date nor unsupported precision may be fabricated or replaced with `null`.

External Version identities are explicit, normalized, and validated independently from internal immutable IDs and access URLs. An `arxiv_revision` stores a canonical modern or legacy base arXiv identifier without an `arXiv:` prefix or `vN` suffix plus a separate positive integer revision number. A `journal_manifestation` stores a lowercase DOI without a `doi:` prefix, resolver URL, or surrounding whitespace when one exists; a genuinely DOI-less manifestation instead requires another stable publisher identifier and a recorded reason. Optional ORCIDs use canonical `0000-0000-0000-000X` form and a valid checksum. Scholarly identity is never encoded only in, or parsed from, an internal Version ID, and resolver or access URLs remain separate fields.

The V0.1 Publication Graph uses `belongs_to`, `revises`, and `published_as`. The concern-file envelope's canonical `work_id` expresses `belongs_to`; it is not duplicated as a separate edge. Explicit `revises` and `published_as` records live in `versions.yaml`. A `revises` relation connects a later curated arXiv revision to an earlier curated revision and does not claim they are adjacent in the complete public revision history. Its endpoints must belong to the same Work and arXiv identity, its revision number must increase from target to source, comparable release dates must not contradict that direction, and the revision graph must be acyclic. Each journal manifestation has at most one incoming `published_as` relation from an explicitly selected arXiv revision; its endpoints must belong to the same Work with source kind `arxiv_revision` and target kind `journal_manifestation`, but no chronological ordering is required. The relation requires a recorded justification and Bibliographic Provenance, is never derived from shared Work membership, and does not assert textual identity.

Version metadata and Publication Relations use Bibliographic Provenance rather than Scientific Evidence. `versions.yaml` stores reusable Work-local `bibliographic_sources`; every source has `id`, `provider`, `record_id`, `source_url`, and `retrieved_at`, with V0.1 provider vocabulary `ads | arxiv | crossref | publisher`. A Bibliographic Source is an immutable retrieval attestation, not the upstream `(provider, record_id)` identity: refreshing the same upstream record creates a new immutable Source ID, preserves the old source, and expresses metadata drift through updated `field_sources` and Bibliographic Discrepancies. Every stored non-derived bibliographic fact on every canonical Version has field-level provenance. `field_sources` maps record-relative RFC 6901 JSON Pointer paths to one or more Bibliographic Source IDs, while Publication Relations reference their supporting source IDs directly. Bibliographic conflicts are preserved as discrepancy records containing the affected field path and conflicting source IDs. Human resolution events are append-only and contain the selected value, normalized reason, and Curation Provenance; current discrepancy state is derived from the event history. Unresolved reader-relevant discrepancies are valid draft curation states but block Work visibility. Publication Relations record `basis: source_asserted | curator_matched`, Curation Provenance, and Review State. `source_asserted` requires an authoritative Bibliographic Source that explicitly connects both endpoints. `curator_matched` requires a normalized reason and at least two meaningful Bibliographic Sources that together cover both endpoints. Agent-created Publication Relations remain unreviewed and are excluded from reader-facing layers until a Human review gate is satisfied; Human creators may self-review under these bibliographic rules, which do not use Bilateral Evidence or the Scientific Edge independent-review rule. Semantic changes to endpoints, relation, basis, normalized reason, or Bibliographic Provenance references reset Review State to unreviewed; formatting-only changes do not.

Evidence, Annotation, Scientific Statement, Causal Link, Scientific Edge, Publication Relation, Research Line Membership, atomically reviewed Learning Path structured content, and Controlled Term governance use the procedural Review State vocabulary `unreviewed | reviewed`. Entity-specific rules determine when reviewed is valid, while lifecycle and disposition remain separate axes. Version metadata, Bibliographic Sources, Actors, Preferred Version selections, Visibility Approvals, and editorial prose do not add a second Review State; their validity follows from provenance, semantic constraints, applicable Human gates, and entity-level Visibility Approval. Human-created Evidence may be self-reviewed for locator and excerpt fidelity, while Agent-created Evidence requires a Human gate before reader-facing use; review of Evidence does not replace review of an assertion that consumes it.

All Curation Provenance creation, review, activation, deprecation, and visibility-approval events use strict UTC RFC 3339 timestamps. Version `release_date` remains a distinct partial-date value rather than an event timestamp.

Every Work explicitly stores `reader_state: draft | visible`. Draft relaxes visibility readiness but never structural, referential, or semantic correctness. A Work may become visible under the V0.1 Visibility Profile only when it has at least one valid Version, a provenance-bearing Preferred Version, renderable `reading.md`, completed assessment of all 16 Physics Ontology axes, at least one reviewed Method Annotation to an active Canonical Technique, compliant Evidence and review for every record exposed in Reader View, and recorded Human release approval. That approval binds to the immutable named Visibility Profile and a deterministic Work-local Visibility Digest computed with the shared canonicalization version and semantic SHA-256 directly from every canonical `content/` input in the approved reader-facing projection, including cross-file dependencies. Generated indexes and every other artifact under `generated/` are never Visibility Digest inputs. Visibility Digests exclude Visibility Approvals, stored or generated digests, Reader State, hidden records, and non-rendered governance metadata. `work.yaml` stores append-only `visibility_approvals`; each record contains the profile ID, attested Visibility Digest, Human reviewer actor ID, and review time. Current approval validity is derived by matching an eligible Human record to the current profile and recomputed digest. Reader-visible changes invalidate the approval, while changes confined to hidden records do not. A visible Work whose approval digest or profile no longer matches is a build-blocking contradiction; the validator reports it and never mutates `reader_state`. Canonical unreviewed records may coexist with a visible Work but remain excluded from every reader-facing layer, including Provenance Detail. Visibility is never inferred from field count, and release-wide Scientific Edge fixture requirements remain separate from per-Work visibility.

Visibility invariants are evaluated against the final repository snapshot rather than an ordered sequence of individual file transitions. Mutually dependent Reader Entities, such as a Work and its anchor Research Line, may therefore become visible atomically in one change set with separate entity-local approvals that match their final projections. V0.1 introduces neither a transient visibility exception nor a Release Batch entity.

Research Lines and Learning Paths are independent Reader Entities with their own `draft | visible` state, profile-bound reader-facing digest, and append-only Human Visibility Approvals stored in `line.yaml` or `path.yaml`. They cannot inherit approval from a Work or from one another, and draft editorial entities have no ordinary reader-facing routes or indexes. The same stale-approval, hidden-record exclusion, offline validation, and no-silent-mutation rules apply to all Reader Entities.

Ownership is persisted once per concern-file envelope: every Work-local YAML file stores a top-level `work_id`, and `reading.md` stores it in frontmatter. Nested Versions, Evidence, Annotations, Statements, Causal Stages, and Causal Links do not repeat ownership. The validator cross-checks every envelope against the Work bundle identity and directory. This is intentional integrity redundancy; paths organize and check records but never supply domain facts.

## 4. Validation

Validation has three build-blocking layers:

1. **Structural**: local shape, types, required fields, and controlled values.
2. **Referential**: every referenced Work, Version, Statement, Controlled Term, Edge, and editorial record exists.
3. **Semantic**: cross-record invariants, lifecycle rules, Evidence requirements, DAG acyclicity, and editorial constraints hold.

Astro or Zod local schemas do not replace cross-record semantic validation.

### Diagnostic Contract

Every diagnostic contains:

```text
severity
code
dataset
file
record_id
field_path
message
related_ids
```

Codes are stable, machine-readable contracts. Tests assert codes and relevant structured context rather than exact human-readable messages.

Every diagnostic `field_path`, like every bibliographic `field_sources` key, is a record-relative RFC 6901 JSON Pointer interpreted together with `record_id`.

Severity semantics are:

- `error`: correctness or invariant failure; blocks the build;
- `warning`: valid but actionable curation debt; does not block;
- `info`: valid state or statistics.

Correctness failures may never be downgraded to warnings, and V0.1 does not treat warnings as errors.

The validator accumulates all reliably discoverable diagnostics. Structurally invalid records are quarantined from dependent passes, while remaining valid records continue through later checks. Each validation pass reports `complete`, `partial`, or `skipped`. Reports are written before a failing process exits non-zero, and validators avoid cascading diagnostics caused by one upstream failure.

Production validation, test, build, verify, and remote CI run fully offline with respect to bibliographic providers and paper sources. They validate canonical source records and URL syntax without fetching external resources. Source availability and metadata refresh belong to a separate explicit workflow and never become an implicit build dependency. V0.1 implements no source-refresh automation or additional refresh acceptance command; that capability is deferred to V0.2.

## 6. Inspection Layers

### Reader View

Presents scientific content without allowing internal governance metadata to dominate normal reading.

The reading experience is academic, information-dense, responsive, and low-noise. Work pages prioritize the Paper title, Scientific Takeaway, scientific structure, and reason-to-read over decoration; core content is available in generated HTML without client-side JavaScript. Research Line pages render their scientific question, relevant physical structure, and reviewed visible memberships. Learning Path pages render the ordered Works and the normalized reason for every adjacent Pedagogical Transition. Work pages render Preferred-Version bibliography and access links, reading prose, assessed Physics Ontology, reviewed Method Annotations, Scientific Statements, Physical Account, Scientific Edges, and Editorial context when those records are reader-visible.

The home page provides the initial research-map and navigation view over visible Works, Research Lines, and Learning Paths without claiming daily refresh. `/papers` provides the complete visible Work index. V0.1 introduces no separate featured-paper lifecycle or manually duplicated `primary_line`, difficulty, or estimated-reading-time fields.

### Provenance Detail

Exposes reasons, Evidence, Version locators, and relevant review context on demand.

Provenance Detail remains reader-facing and therefore excludes every hidden unreviewed record.

### Validation Report

Reports governance state and proves structural, referential, and semantic invariants for the complete V0.1 dataset.

Validation always attempts to emit ignored generated reports at:

```text
validation/report.json
validation/report.md
```

JSON serves CI, tests, and agents. Markdown serves human review. Validation failures still emit both reports and block the build. V0.1 adds no public validation route.

## 9. Curation Actor Policy

- A global canonical `actors.yaml` registry assigns every actor an immutable ID, `kind: human | agent`, display label, and explicit project-granted capabilities.
- Actor Registry mutation is repository-level governance outside the five V0.1 content capabilities. V0.1 adds no application-level actor administration or self-authorizing capability.
- V0.1 freezes five capabilities: `draft_records`, `review_records`, `independent_scientific_review`, `activate_controlled_terms`, and `approve_visibility`.
- Capabilities are temporally scoped append-only records containing `capability`, `action: grant | revoke`, `effective_at`, and reason. Authorization is evaluated against the capabilities in force at the action timestamp, so later grants do not retroactively authorize old actions and later revocations do not invalidate actions that were authorized when performed.
- Curation Provenance distinguishes human and agent actors by actor type and stable actor ID without storing credentials or secrets.
- Agents may retrieve Evidence and draft scientific records.
- V0.1 Agent actors receive only `draft_records`; Human actors receive other capabilities only through explicit grants.
- Agent-created records remain unreviewed until a Human Review Gate is satisfied.
- Production independent review of Inferred assertions and Controlled Term activation requires an eligible Human reviewer.
- Different agents do not constitute production review independence.
- Validators enforce Human-only gates and actor capabilities; actor identity is never inferred from display names, Git authors, CI accounts, or credentials.

## 10. Source Snapshot Policy

V0.1 neither requires nor commits paper source snapshots. Canonical Evidence uses Version identity, a stable source reference, a typed locator, and a short excerpt. Temporary ignored caches are non-canonical, and checksums are recorded only for genuinely managed and retrievable snapshots.

## 11. Synthetic Fixture Isolation

Synthetic validation datasets live only under:

```text
tests/fixtures/
  valid/
  invalid/<invariant-name>/
```

- Production loaders never scan the fixture root.
- Each invalid fixture declares its exact expected validator error code.
- Fixture reports identify their dataset explicitly.
- Fixture records never enter production indexes, counts, routes, or pages.
- Tests prove that production and fixture roots cannot be mixed.

## 12. Verification Commands

V0.1 freezes these commands:

```text
npm run validate
npm run test
npm run check
npm run build
npm run verify
```

- `validate` attempts to generate JSON and Markdown reports on success or failure.
- `test` covers units, valid and invalid fixtures, and loader isolation.
- `check` performs Astro and TypeScript static checks.
- A direct production `build` remains validation-gated.
- `verify` runs validation, tests, static checks, and the production build and is the single V0.1 completion proof.

The repository README documents local setup, the frozen verification commands, and how to add or revise a Work, Research Line, and Learning Path without bypassing validation or review gates.

## 13. Deployment Boundary

V0.1 requires both a local `npm run verify = 0` result and a real clean-environment remote CI pass, but not external site deployment. Hosting platform selection is deferred to a later decision.

Before implementation planning:

2. reconcile and migrate valid requirements from `spec_mvp_v0.1.md`;
